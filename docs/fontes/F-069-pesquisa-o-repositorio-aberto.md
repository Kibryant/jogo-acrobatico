## §1 — Plano Free com repositório público: Actions, proteção de branch, rulesets

- Fato: minutos de Actions em repositório público com runners padrão são gratuitos. "GitHub Actions usage is free for self-hosted runners and for public repositories that use standard GitHub-hosted runners." Runners maiores são sempre cobrados. Fonte: https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions
- Fato: em repositório público, o runner Linux padrão tem 4 vCPU, 16 GB de RAM e 14 GB de SSD. Em repositório privado tem 2 vCPU e 8 GB. Fonte: https://docs.github.com/en/actions/reference/runners/github-hosted-runners
- Fato: o plano Free tem 2.000 min/mês para repositórios privados, 500 MB de artefatos e 10 GB de cache por repositório. Cache é 10 GB por repositório em todos os planos. Fonte: https://docs.github.com/en/actions/reference/limits
- Fato: no plano Free são 20 jobs concorrentes (5 de macOS). Cada job pode rodar até 6 horas. Mesma fonte.
- Fato: a retenção de artefatos e logs em repositório público pode ser ajustada entre 1 e 90 dias, e o padrão é 90. A página diz que, a partir de 1º/10/2026, essas políticas também cobrem checks, workflow runs e commit statuses. Fonte: https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository
- Inferência: com o repositório público, o CI do Arthur deixa de consumir a cota de 2.000 minutos e passa a rodar em runner de 4 vCPU. A cota de 500 MB de artefatos continua a valer para o plano. Os builds para Releases não dependem dela.
- Fato: proteção de branch e rulesets funcionam em repositório público no plano Free. Eu não consegui citar uma frase literal da documentação que diga isso. O que há é um resumo de busca, não verificado: "rulesets are offered in public repositories on GitHub Free". A página "About rulesets" aberta diretamente não menciona o plano Free. Além disso, "Bypass lists can only be configured for repositories that belong to an organization" vale para a proteção de branch clássica.
- Fato: o ruleset oferece "Require a pull request before merging", "Require status checks to pass", "Block force pushes" e "Require linear history". Fonte: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets
- Fato: a quantidade de aprovações exigidas vai de 0 a 10: "Required approvals can be set from 0 (zero) to 10." Mesma fonte.
- Fato: o ruleset aceita bypass por papel, time ou app. O modo "For pull requests only" obriga o ator a abrir PR em vez de dar push direto. Fonte: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository
- Fato: na proteção clássica, "By default, the restrictions of a branch protection rule do not apply to people with admin permissions." Existe a opção "Do not allow bypassing the above settings". Fonte: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches
- Recomendação: para um mantenedor solo, usar um ruleset com PR obrigatório, aprovações em 0, status checks obrigatórios (o job do gate), force push bloqueado e histórico linear. Assim o Arthur não precisa aprovar o próprio PR. Se quiser um escape para emergências, pode pôr o papel Repository admin na bypass list em modo "For pull requests only".
- Fato: relatos da comunidade dizem que o bypass de admin pode se comportar diferente entre os modos Evaluate e Active. É um relato isolado. Fonte: https://github.com/orgs/community/discussions/153705
- Recomendação: testar com um PR real com o ruleset em Active antes de confiar no bypass.

## §2 — Segurança do Actions com PRs de forks

- Fato: o repositório pode exigir aprovação manual para workflows de PRs de forks. "Workflow runs triggered by a contributor's pull request from a fork may require manual approval from a maintainer with write access." Runs que aguardam aprovação por mais de 30 dias expiram. Fonte: https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-workflow-runs/approving-workflow-runs-from-public-forks
- Fato: as opções em Settings > Actions > General são: "Require approval for first-time contributors who are new to GitHub", "Require approval for first-time contributors" e "Require approval for all external contributors". Fonte: https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository
- Recomendação: usar "Require approval for all external contributors" enquanto o projeto é pequeno. O custo é o Arthur clicar em aprovar a cada PR externo.
- Fato: o `GITHUB_TOKEN` padrão em repositório de conta pessoal só tem leitura em `contents` e `packages`. Mesma fonte.
- Fato: o guia de hardening manda evitar `pull_request_target`: "Avoid using the `pull_request_target` workflow trigger if it's not necessary." Workflows com esse gatilho "must not explicitly check out untrusted code, including from pull request forks". Fonte: https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions
- Fato: no gatilho `pull_request`, PRs de forks rodam sem secrets e com token de leitura. As opções "Send write tokens" e "Send secrets" que liberam isso aparecem na página de configurações para repositórios privados. A página não afirma o comportamento padrão para público. É conhecimento geral, não confirmado nessas páginas.
- Fato: sobre runners self-hosted, o guia diz que "should almost never be used for public repositories" porque "any user can open pull requests against the repository and compromise the environment". Eles podem ser comprometidos de forma persistente.
- Recomendação: manter `pull_request` (nunca `pull_request_target` com checkout do PR). Definir `permissions: contents: read` no workflow. Reservar o job de exportação e Release para tags, onde o Arthur controla o código. Não usar runner self-hosted.

## §3 — Git LFS em repositório público

- Fato: a cota gratuita do Free é de 10 GiB de armazenamento e 10 GiB de banda. Fonte: https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-storage-and-bandwidth-usage
- Fato: "When you download a Git LFS file, the bandwidth you use is included in the repository owner's bandwidth usage." A página não faz distinção entre repositório público e privado.
- Fato: "If GitHub Actions downloads a 500 MB file that is tracked with Git LFS, it will use 500 MB of the repository owner's bandwidth." Mesma fonte.
- Fato: "Forking and pulling a repository counts against the parent repository's bandwidth usage." Mesma fonte.
- Fato: sobre clones anônimos, a página não diz nada. Por isso não está confirmado se cada clone de um estranho consome a banda do Arthur. Pela regra literal, consome.
- Fato: é possível enviar objetos LFS a forks públicos: "You can push Git LFS objects to public forks if the repository network already has Git LFS objects". Isso conta na cota do repositório pai: "count against the parent repository's bandwidth and storage quotas". Fonte: https://docs.github.com/en/repositories/working-with-files/managing-large-files/collaboration-with-git-large-file-storage
- Fato: se o armazenamento estoura e não há forma de pagamento, ainda dá para clonar, mas só vêm os arquivos ponteiro. Fonte: a mesma página de storage and bandwidth.
- Fato: `actions/checkout` tem `lfs` com padrão `false` ("Whether to download Git-LFS files"). Fonte: https://github.com/actions/checkout
- Inferência: com 110 KB em LFS hoje, o risco é pequeno. Ele cresce com arte, áudio e modelos 3D. Cada clone completo de um estranho baixa todo o LFS do checkout.
- Recomendação: usar `lfs: false` nos jobs que não precisam de binários (lint, testes do core). Nos jobs que precisam, usar `actions/cache` com chave pelo hash do `.gitattributes` e `git lfs ls-files`. Medir a banda no painel de billing. Considerar manter assets pesados fora do LFS do repositório público, em Releases.

Secret scanning e push protection estão "Available for public repositories by default". Code scanning também. Fonte: https://docs.github.com/en/code-security/getting-started/github-security-features

- Fato: a política de segurança (SECURITY.md) está disponível em todos os planos. A página geral não nomeia o relato privado de vulnerabilidade. Fonte: a mesma de segurança.
- Fato: "Owners and administrators of public repositories can allow security researchers to report vulnerabilities securely." Para ligar: Settings > Advanced Security > Private vulnerability reporting > Enable. Fontes: https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability e https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/configuring-private-vulnerability-reporting-for-a-repository
- Recomendação: ligar secret scanning, push protection, Dependabot alerts e o relato privado, e criar um SECURITY.md curto.

## §5 — Mudar a visibilidade de privado para público

- Fato: a página diz que "Actions history and logs will be visible to everyone." Se o repositório usa workflows compartilhados, o caminho do arquivo com o nome do repositório aparece nos logs. Fonte: https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility
- Fato: "Stars and watchers for this repository will be erased", forks privados são desvinculados ("GitHub will detach private forks and turn them into a standalone private repository") e o repositório ganha as features de Advanced Security. A página também diz que "All push rulesets will be disabled."
- Fato: a página não menciona artefatos, LFS nem secrets. Isso não está confirmado.
- Inferência: os artefatos antigos ainda guardados ficam visíveis junto do histórico do Actions. Podem conter builds ou logs com dados pessoais.
- Recomendação: checklist antes de publicar:
  1. Rodar gitleaks no histórico completo, incluindo todas as branches, tags e refs.
  2. Revisar os logs e artefatos de Actions antigos e apagar os desnecessários.
  3. Revisar `docs/fontes` (transcrições literais) e os diários em busca de dados pessoais, nomes de terceiros e conteúdo que o Arthur não queira publicar.
  4. Conferir a licença de cada addon vendorizado (gdUnit4, netfox) e os pacotes em `assets/third_party`, com os arquivos de licença e `CREDITS.md`.
  5. Escolher a licença do repositório. O SignPath exige licença OSI (seção 7).
  6. Decidir a questão do e-mail (seção 6) antes de publicar, porque depois não dá para desfazer.

## §6 — Dados pessoais no histórico: e-mail do autor

- Fato: "Keep my email addresses private" vale para operações web, e "Block command line pushes that expose my email" bloqueia pushes cujo commit mais recente tem seu e-mail privado. Fonte: https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-email-preferences/blocking-command-line-pushes-that-expose-your-personal-email-address
- Fato: "Any commits you made prior to changing your commit email address are still associated with your previous email address." Fonte: https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-email-preferences/setting-your-commit-email-address
- Fato: o formato do endereço noreply não foi confirmado nas páginas abertas. O formato conhecido é `ID+USUARIO@users.noreply.github.com`, mas a página de e-mail aponta para uma referência que não consegui abrir.
- Recomendação: antes de qualquer push novo, ligar as duas opções e configurar `git config user.email` com o endereço noreply. Isso só protege os commits futuros.
- Fato: o `git filter-repo` aceita `--mailmap` (só consulta a versão atual do arquivo), `--use-mailmap` (equivale a `--mailmap .mailmap`) e `--email-callback`. Fonte: https://raw.githubusercontent.com/newren/git-filter-repo/main/Documentation/git-filter-repo.txt
- Fato: o autor recomenda remover a URL do `origin` como medida de segurança. Sobre LFS, o manual avisa que objetos antigos "need to be deleted/purged from the LFS server". Mesma fonte.
- Fato: o filter-repo trabalha numa cópia nova do repositório, e referências a hashes nas mensagens de commit não são reescritas. Fonte: https://github.com/newren/git-filter-repo
- Inferência: reescrever o histórico muda todos os hashes. Isso quebra referências a commits nos docs do projeto (as F-xxx, DEC, diários), tags, PRs já mergeados e clones existentes. Os ponteiros LFS não mudam de conteúdo, mas os objetos dependem da cota e do repositório.
- Inferência: um `.mailmap` só muda a exibição local no `git log` e no `shortlog`. O e-mail continua no objeto do commit e visível na API.
- Fato: o GitHub não apaga o que ficou para trás sozinho. "If you only rewrite your history and force push it, the commits with sensitive data may still be accessible elsewhere": por SHA-1 em views em cache, em forks e em PRs. "GitHub Support won't remove non-sensitive data". Fonte: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository
- Fato: refs `refs/pull/` são somente leitura e o push delas falha.
- Recomendação: como o repositório ainda é privado e sem forks, o caminho mais limpo é reescrever o e-mail com `--mailmap` em um clone novo e publicar assim. Alternativa: publicar um repositório novo a partir de um snapshot, com o histórico reescrito ou sem histórico, e manter o atual como arquivo privado. A segunda opção evita PRs e refs antigos com o e-mail, ao custo de perder a história pública. Decidir antes de mudar a visibilidade. E-mail do Gmail pessoal é um dado que o Arthur pode considerar aceitável expor. É decisão dele.

## §7 — Assinatura de código gratuita para builds Windows

- Fato (SignPath Foundation): "For OSS projects, our services are free of charge." O certificado fica ligado ao repositório, a chave privada fica num HSM, e não é preciso identificação pessoal ("No need for personal identification."). Fonte: https://signpath.org/
- Fato: requisitos: "The project must use an OSI-approved Open Source license without commercial dual-licensing for all components"; sem malware; projeto mantido e já lançado; funcionalidade descrita na página de download. "Binary artifacts must be built from source code in a verifiable way." "Every release needs manual approval for signing." Fonte: https://signpath.org/terms.html
- Fato: o publicador exibido é a SignPath Foundation, não o Arthur. O site precisa de uma política de assinatura com a frase "Free code signing provided by SignPath.io, certificate by SignPath Foundation." Mesma fonte.
- Fato: a página de candidatura não mostrou critérios (ela abriu quase só com navegação). Não confirmado: exigência de repositório público, de GitHub Actions, de popularidade ou se indivíduos podem se candidatar.
- Fato (Certum): o kit "Open Source Code Signing" aparece "from €69.00 gross", com cartão criptográfico, leitor e requisitos como chave RSA de 3072 bits. A página mostra "out of stock" e "In stock" ao mesmo tempo e não declara a validade do certificado. Fonte: https://shop.certum.eu/open-source-code-signing.html
- Fato: um resumo de busca diz que o certificado Open Source é emitido só para indivíduos, que o projeto precisa ser público e que a verificação de identidade tem três métodos. Não confirmado em fonte primária. Esse resumo também cita relatos antigos de que o certificado Open Source não serviria para Authenticode, e que a assinatura em nuvem (SimplySign) exigiria intervenção humana. Não confirmado, e não há informação sobre indivíduos no Brasil.
- Fato (Azure Artifact Signing): "Public Trust certificates are available to organizations in the United States, Canada, the European Union, the United Kingdom, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway, and Israel. Individual developers must be located in the United States or Canada." Fonte: https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart (atualizada em 08/10/2026).
- Fato: preço de partida de US$ 9,99/mês. Fonte: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation. O limite de 5.000 assinaturas e o plano de US$ 99,99 vêm só de um resumo de busca da página de preços. Não confirmado em fonte primária.
- Inferência: o Arthur é pessoa física no Brasil, então o Azure Artifact Signing não está disponível para ele hoje. Um CNPJ brasileiro também não resolveria: o Brasil não está na lista de organizações.
- Fato (SmartScreen): "EV certificates no longer bypass SmartScreen" e pagar a mais por EV só para evitar avisos "is no longer justified". Certificado válido (OV ou EV) ainda gera aviso até acumular reputação. Fonte: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation (atualizada em 17/08/2026).
- Fato: a reputação vem de dois sinais, a do publicador/certificado e a do hash do arquivo. "There is no exact threshold, but it can take several weeks and hundreds of clean installs from a wide audience." Arquivos sem assinatura recomeçam do zero a cada versão. Mesma fonte.
- Fato (Smart App Control): "Malware, Potentially Unwanted Apps (PUA), and unknown, unsigned code are blocked by default." Se o serviço de inteligência não consegue prever, o app roda se estiver assinado por uma CA do Trusted Root Program. Fonte: https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview (atualizada em 06/10/2026).
- Fato: "Smart App Control will block execution of unsigned files unless the file has a positive reputation", e a checagem vale para todos os executáveis, não só os baixados. Fonte: a página de SmartScreen reputation.
- Inferência: sem assinatura, amigos com o Smart App Control em modo de imposição só rodam o build se a Microsoft já o conhecer, o que não acontece com um jogo novo. Eles precisam desligar o recurso (e ele só volta com reinstalação do Windows). Com assinatura de uma CA confiável, o app passa pelo Smart App Control, mas ainda pode mostrar aviso do SmartScreen no começo.
- Recomendação: a rota mais realista é candidatar-se ao SignPath Foundation depois de publicar o repositório com licença OSI. A Certum é plano B, mas exige confirmar com ela o fluxo para indivíduos no Brasil. Enquanto isso, avisar os testadores sobre o aviso do SmartScreen e do Smart App Control.

## §9 — Resumo

- Fato: Actions em repositório público com runner padrão é gratuito e o runner Linux passa a ter 4 vCPU e 16 GB (Seção 1). O CI deixa de gastar a cota de 2.000 minutos.
- Fato: a cota de LFS (10 GiB de banda) é do dono do repositório, vale para downloads de estranhos e Actions, e o push de LFS em forks públicos conta na cota do repositório pai (Seção 3). É o maior risco de custo do projeto.
- Recomendação: usar `lfs: false` nos jobs que não precisam de binários e cachear o LFS nos que precisam.
- Fato: proteção de branch e rulesets funcionam em repositório público no Free, mas não achei frase literal da documentação para citar (Seção 1). Um ruleset com PR obrigatório e 0 aprovações, mais checks obrigatórios, resolve o caso do mantenedor solo.
- Recomendação: exigir aprovação de todos os contribuidores externos, usar `pull_request` (nunca `pull_request_target` com checkout do PR), token só de leitura e nenhum runner self-hosted.
- Fato: ao publicar, o histórico de Actions fica visível e as estrelas são zeradas (Seção 5). Rodar o gitleaks no histórico inteiro e revisar logs e artefatos antigos antes.
- Fato: o e-mail pessoal do Gmail nos commits ficará público, e mudar a configuração só protege commits futuros (Seção 6). Reescrever tudo muda todos os hashes e o GitHub não apaga forks nem caches. Decidir antes de publicar.
- Fato: o Azure Artifact Signing só atende pessoas físicas nos EUA e no Canadá (Seção 7). O Arthur no Brasil não pode usá-lo.
- Recomendação: o SignPath Foundation (gratuito, exige licença OSI) é a melhor opção, mas o publicador exibido será a SignPath Foundation.
- Fato: EV não evita mais o SmartScreen, e o Smart App Control bloqueia código não assinado sem reputação positiva (Seção 7). Sem assinatura, testadores com o Smart App Control ativo não conseguem rodar o build.

## §10 — Não confirmado

- Frase literal da documentação dizendo que proteção de branch e rulesets estão disponíveis em repositório público no plano Free. A página "About rulesets" aberta não menciona o plano Free. Só há resumo de busca.
- Clones anônimos de repositório público consumirem a banda LFS do dono: a página não trata do caso.
- Formato exato do e-mail noreply (a página aberta não o traz).
- Que PRs de forks recebem por padrão token de leitura e nenhum secret no gatilho `pull_request` em repositório público: conhecimento geral, não encontrado nessas páginas.
- Requisitos de candidatura do SignPath (repositório público, CI, popularidade, indivíduos): a página de candidatura não os trouxe.
